=====================================================

tests/test_l1_slice.py. The brain (experiments/skills_sim/brain, a client of the robot protocol on a
real asyncio clock) drives the MuJoCo WidowX server (experiments/skills_sim/sim_server.py,

Judged from the server's world() with trials.judge(): every block resting inside its slot's radius,
gripper empty, arm back at travel height.

Scene: blocks 5, 1, 3 at x 0.26, y +0.12 / 0 / -0.12 (left to right as the robot sees them), a

What broke, and what changed
----------------------------

Nothing in the brain or the server broke: the four scenarios passed on the first run, and the
numbers held over three runs. The only mismatch surfaced was one of capability, not of behaviour:
the sim server has no way to put a hand into the world (nothing in its scene is a person, world()
always reports hands=[]), so scenario (c) could not be run from the sim's side. Rather than teach
the physics about hands (a body the arm could hit would need its own contact handling and would not
be how the real robot sees hands anyway), I added a perception override in front of the server,
ScriptedPerception in skills_sim/brain/mocks.py: a pass-through RobotServer that reports a scripted
HandObs in world().hands, sends the scene_change a perception process would, and logs every tool
call and every arm-mode change with the wall time (the same class gives (a), (b) and (d) their
measurements). It is a test double; the Brain never imports mocks.py. Two smaller changes:
ScriptedUser's attach time is now a public `t0`, so a test can put "when the text was typed" and
"when the server reported holding" on the same clock; and the sim_server module docstring said STOP
fails skills with the code "stalled" while the code (correctly) uses the catalog's "stopped" -- the
docstring now matches. No test was loosened; protocol.py and catalog.py were not touched.

Things the protocol or the catalog made awkward (report, do not settle)
----------------------------------------------------------------------

- Place ids. The sim says slot_0..n-1, the stub and e12v2's scenarios say tray_slot_1..n. e12v2's
  oracle orders a sorting plan by parsing "tray_slot_<k>" (eval/oracle._rank), so on the sim it falls
  back to the Goal's dict order: the mock planner's step order is whatever order the test wrote the
  Goal in. Harmless with the oracle, but it is why the test builds Goal({...}) by hand instead of
  reusing scenarios.sort_goal(). Already on the follow-ups list; L1 confirms it bites.
- Hands are a resource with no source. protocol.WorldState carries hands and the brain reacts to
  them, but nothing on the server side of the protocol produces them, and the protocol's only
  notification for a hand is the generic scene_change. The measurement above shows the 0.5 s bar
  wants that notification: polled, the brain is at 0.3 s typical and ~0.5 s worst case.
- Mid-skill phase. The protocol gives a skill's phase only through status(skill_id); a test that
  wants "while carrying" has to read ArmObs.skill (which the sim fills and the stub does not, as the
  follow-ups note) and then status() it. Fine, but two calls and a field the brain does not use yet.
- STOP's end state is the server's choice. The sim keeps the grip and parks with the block in hand;
  the stub sets the block down. Both satisfy "set down or held, never dropped", and the brain does
  not care, but the protocol docstring for stop() does not say which a server should do.
- Cancellation by start(). A correction replaces the held skill by starting the next one on a busy
  arm (no cancel tool, no event for the replaced skill). It worked here because the new
  pick_and_place notices the object already between the fingers; a skill that did not would have to
  release and re-grasp. Worth a line in the catalog: a grasping skill started with its object in the
  gripper carries on from there.
