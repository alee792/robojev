# v2: one decision per event

v1 showed that Jev can run inside a real-arm control loop (138 ms median, no errors) and is good at
matching words to objects and places. It did not show that Jev beats a script: the task was
scriptable, and the script ended up in its prompt (`docs/assessment.md`). v2 gives each part only the
job it is good at: an LLM plans, Jev decides what each surprise means and who should handle it, and
code moves the arm.

## Principles

- **The LLM reasons, skills move, Jev judges meaning, code does the numbers.** The LLM turns the
  task into motor actions (sorting, choosing, ordering are reasoning). Skills are motor control only:
  they know how to move the arm, not why. Jev picks among options code has already checked. Code
  owns geometry, arithmetic and limits.
- **The LLM stays off the critical path.** Apart from the first plan, the arm never waits
  mid-motion for an LLM: it carries on, or holds at a safe point.
- **Nothing is prepared for deviations in advance.** The plan covers the task as asked. A correction
  or surprise the plan can't absorb goes to the LLM when it happens.
- **Ask Jev only what code can't answer**, and show what gets worse without each question.
- **Safety never depends on a model.**

## Parts

| Part | Runs on | Job |
|---|---|---|
| Perception | VLM + depth/tracking | Keep the world state: every object, where it is, what it is. Flag changes the robot didn't cause |
| Planner | LLM: a fast model, or a capable one | Write the plan at the start of an episode; replan when a decision hands off to it |
| Decision | Jev | For each event, answer three groups of questions in one request (below) |
| Harness | Code | Hold the plan and world state; turn events into decisions; apply the answers; run the plan steps |
| Skills | Code (VLA policies later) | Motor control: carry out one plan step; report done or failed |
| Safety filter | Code | Clip every command to workspace, speed and constraints |

## Terms

| Term | Meaning |
|---|---|
| Episode | One task, from the user asking to done, stopped, or given up |
| Task | What the user asked for: the final arrangement. The order of moves is up to the plan unless the user says otherwise |
| World state | Objects (id, name, position, attributes) plus robot state (holding, current step, last result) |
| Plan | From the LLM: an ordered list of plan steps, the conditions that mean the task is done, and any constraints (below) |
| Plan step | One skill call with its objects filled in: `move_object(red_1, left_bin)` |
| Skill | A motor capability: how to move an object somewhere, hand it over, stack it. No task logic |
| Done condition | A plain statement the LLM writes and Jev checks: "red_1 is in the left bin" |
| Event | Anything that needs a decision: a plan arrives, a step finishes or fails, the scene changes, the user types |
| Decision | One Jev request with three question groups, plus code combining the answers |
| Route | Who handles an event: stay local, fast LLM, capable LLM, or ask the user |
| Constraint | A rule that holds for the whole task ("don't touch the green one"). It attaches to a tracked object, so it moves with it |
| Safety filter | Code that clips every command to limits and constraints |

## An episode

Two loops run at different speeds:

- **The control loop** (code, ~100 Hz) moves the arm through the current plan step, with the safety
  filter on every command. Jev is not involved.
- **The decision loop** runs only when an event happens. Each decision takes ~150 ms.

```
episode(task):
    plan = fast_llm(task, world)              # the one planned wait (~2-3 s, E13)
    start plan step 1                          # don't wait for the plan check
    decide("new plan")                         # async; a problem it finds is just another event
    until done:
        run the current plan step              # code, ~100 Hz, safety filter on every command
        on any event (plan arrived, step done/failed, scene change, user text):
            a = jev(event, where we are in the plan, nearby objects)   # all three groups, ~150 ms
            apply a.right_now                  # carry on, pause, back off, re-target
            if a.route == stay_local and confident:
                apply a.in_plan_fix            # retry, skip, re-queue, next step
            else:
                hold at a safe point
                plan = llm(a.route, task, world, plan, event)   # fast or capable
                decide("new plan")
```

Worked through for "Put the red blocks in the left bin":

| Time | Event | Decision | What happens |
|---|---|---|---|
| 0-3 s | Task arrives | none | Fast LLM writes the plan: red_1, red_2, red_3 → left bin (the one planned wait) |
| 3 s | Plan arrived | Checked in parallel: plan matches the task | Step 1 starts at once: pick red_1 |
| 8 s | Step finished | red_1 is where the task wants it; next step | Step 2: pick red_2 |
| 10 s | Scene: red_2 slid aside | Right now: re-target. Route: stay local | Arm follows red_2 |
| 13 s | User: "actually, right bin" | Right now: finish placing the block in hand. In-plan fix: none. Route: fast LLM | Arm holds at a safe point; LLM replans, including moving red_1 back out (~3-4 s, up to 25 s) |
| 17 s | Plan arrived | Checked: matches the corrected task | Carry on |
| 18 s | Scene: hand reaches toward arm | Right now: pause (the code stop distance applies regardless) | Arm pauses |
| 19 s | Scene: hand gone | Right now: resume | Arm resumes |
| 35 s | Step finished | Every red block is where the task wants it | Episode over |

Most decisions are the routine "step finished" kind. The interesting ones are the few whose route
is not "stay local".

## The decision

Every event, whatever its source, gets the same request shape: the event, where the arm is in the
plan, and the objects near it. It carries three groups of questions, answered in parallel (TypeSafe's
speculative fan-out: asking more questions in one request costs no latency, and code ignores the
answers that don't matter for this event).

| Group | Question | Answers |
|---|---|---|
| **Spotter** | What should the arm do right now? | carry on, pause, back off, re-target, resume |
| **Sequencer** | Can this be fixed within the current plan? | retry, skip, re-queue an object, go to a different plan step, none |
| **Router** | Who handles it? | stay local, fast LLM, capable LLM, ask the user |

Code combines them:

1. The **right-now** answer applies immediately. A typed "wait" is a pause just like a hand reaching
   in.
2. The **in-plan fix** applies only if the Router says stay local and the confidence is high.
3. Otherwise the arm holds at a safe point and the fast or capable LLM replans from where things
   stand.

Which groups matter depends on the event: user chatter needs none of them to act; a hand usually
needs only right-now; "actually, right bin" needs the Router; a finished step is mostly the
Sequencer's progress check.

**Progress checks ask one question per done condition**, not "is the task on track?": "Is it true
that red_3 is in the left bin?", with code comparing the answers against the plan. The holistic
question is the multi-step reasoning Jev is weak at. Where code can measure a condition directly
(the block's position is inside the bin), code checks it and Jev isn't asked. A plan check works the same way,
with yes meaning something is wrong: "Is `red_3` something the task asks about but the plan leaves
out?" This is TypeSafe's SDE cascade (cheap model, Jev check, expensive model only when it fires).

**Confidence decides escalation**, never a question asking Jev whether it is sure: in E11 that
question separated right answers from wrong ones no better than chance, while the weakest confidence
among the questions an action depends on did. Each route has its own threshold, set by what a wrong
answer costs: low for pause (it is cautious), high for stay-local and resume. Below it, the decision
escalates, and a low-confidence detail falls back to the cautious choice in code.

## The plan

The LLM reasons from the task to motor actions. An example plan for "put the red blocks in the left bin,
and don't touch the yellow one":

```json
{
  "steps": [
    {"skill": "move_object", "object": "red_1", "to": "left_bin"},
    {"skill": "move_object", "object": "red_2", "to": "left_bin"},
    {"skill": "move_object", "object": "red_3", "to": "left_bin"}
  ],
  "done_when": ["red_1 is in the left bin", "red_2 is in the left bin", "red_3 is in the left bin"],
  "constraints": ["don't touch yellow_1"]
}
```

The same shape covers tasks that aren't about arranging things: a handover is
`hand_over(red_1)`, done when "the person is holding red_1"; a tower is ordered `stack_on` steps; a
standing rule ("keep the green one off the tray") is a constraint. When a step can't run (its
target slot is occupied), that is an event, and the in-plan fix can run another step first.

Output is structured (a strict JSON schema, with object ids and places as fixed lists from the
world state) and kept small: a replan returns only what changes. The unchanging part of the prompt
(instructions, skill list) is cached.

## Skills

The first set is small and motor-only: `move_object(object, place)` (pick, carry, place),
`hand_over(object)`, `stack_on(object, base)`, `push(object, direction)`, `survey`, `hold`.

```
precondition(world_state) -> bool   # only steps that can run now are offered
start(args)                         # objects from the plan step
step()                              # a short chunk of motion; the safety filter clips it
status() -> running | done | failed(reason)
```

Skills are scripts for now. The interface is the same one a VLA policy would use, so a dexterous
skill can be added later without changing anything around it.

## Writing Jev questions

From TypeSafe's jaggedness notes and cookbooks, and E11/E12. The LLM's question templates follow
these too.

- **Code does the arithmetic.** Counting, ranking, distances and comparisons are computed; Jev gets
  the result or a named band ("near", "in the arm's path").
- **One judgment per question, one hop.** Loop over objects in code and ask each one directly.
- **Don't ask what code can look up.** Asking Jev for something code already knows invites
  contradictions (in E11 its direction contradicted its own slot in 24/103 answers).
- **Say exactly what you mean.** Jev reads literally: state the condition, put boundary cases in
  the criteria, and keep instructions and criteria saying the same thing.
- **Checks: yes means something is wrong.**
- **Name positions by role, not number** ("the leftmost free slot", "the held block's goal").
  Arbitrary numbers halved slot accuracy in E11.
- **State where the arm is in the plan step, literally** ("lowered at red_1's goal, not yet
  released"). One missing fact of this kind failed every E12 `raw` run.
- **Draw boundaries between competing options** with `not_for` in the criteria.
- **Ask about the action wanted, not the subject.** "Is the user asking the robot to do something
  different?" separates a correction from chatter; "is this about the blocks?" does not.
- **No voting on choices.** Below a confidence floor the answer is "uncertain" and escalates.
- **Filter the state** to the event and what's near it; irrelevant detail costs accuracy.

## Rules that hold everywhere

- Priority: STOP button > safety filter > right-now answer > route > in-plan fix > plan.
- STOP never depends on a model: the STOP button, and "stop" typed by the user, act in code. A model
  can only pause the arm; it resumes when the user says so or a decision says resume.
- Perception only flags changes the robot didn't cause. Code keeps a simple expectation of what the
  robot itself moves: the held object travels with the gripper, and objects within a few cm of a
  grasp may shift.
- A loop is a failure: the same two plan steps alternating more than twice escalates.
- Decisions run on events, never on a clock, which keeps them well under the 20 requests/s account
  limit.

## Data capture

Every episode records every Jev request and answer, every LLM call, the world state at each decision
and a camera frame at each event. A decision someone marks wrong gets its correct answer attached, and
the growing set is re-run on every prompt change.

The dashboard shows each decision, route and plan change as it happens, and is where a wrong decision
gets marked. Its design gets its own pass.

## Stages

- **Crawl:** sort blocks into bins or a tray on a static table, with several different tasks and no
  code changes. Scripted skills; build in sim, accept on the real arm. Perception stays cheap:
  coloured, numbered blocks, an overhead camera with AprilTag calibration, colour plus depth for
  position, and a VLM only to read each block's number once.
- **Walk:** a person interferes and corrects: moves the target, takes a block back out, reaches into
  the path, changes the task mid-run. Pass = the task still finishes, with no contact with the hand.
  Compared against the same system with Jev replaced by hand-written rules, including some changes
  and corrections the rules can't anticipate.
- **Later:** VLA skills for objects a script can't handle, and a Planner that streams its plan in
  pieces so the first steps run while it works out the rest.

**Held-out tests.** Every test set keeps tasks and corrections we never tune prompts on, reported
separately: at least a stack, a handover and a standing rule, which don't fit "sort these blocks",
and corrections written by someone else or generated from a different prompt. This is v1's
paper-cup lesson applied to the prompts.

**Headline demo:** the task changes in plain language mid-run ("actually, right bin"), with no
restart. Jev reads the correction and routes it within ~150 ms; the arm finishes its current move
and holds; the fast LLM replans in a few seconds (E13: 2.7–4.1 s median, 6–7 s p95).

## What the spikes say

E11 and E12 ran against `jev-1.13.0` on 2026-09-23 (`context/08-experiment-results.md`). E12 tested
an earlier version of this design (a Listener for user text, a Spotter for hands only, a Sequencer
that picked the next skill).

- **Jev reads corrections almost perfectly and can't work out moves.** "Actually, reverse it" and
  similar were understood 719/720 times; the move itself was right only ~75% of the time, worse with
  arbitrary block numbers. Given the answer for each reading, it chose right 301/303. So Jev decides
  what a correction means and where it goes; it does not compute the new arrangement.
- **Confidence flags mistakes.** Trusting Jev only at 70% confidence or more caught 71 of its 72
  mistakes in E11. A question asking Jev whether it is sure did not work (no better than chance).
- **State facts literally.** E12's `raw` runs all stuck at the first block because nothing said
  "lowered at the goal, not yet released"; that says more about the state than about Jev.
- **The reflex group earns its place.** With the Spotter off, the simulated hand was touched in 3/3
  runs; with it on, 0/4. (E12's Spotter restated the oracle's thresholds, so this is close to a
  lookup; the E12 update removes that.)
- **Latency is fine for events.** Decisions took 150/260 ms p50/p95.

- **E13 (2026-09-24): prepared variants don't happen; replanning costs seconds.** Asked for a plan
  with optional variants, `gpt-5.6-terra` and `gpt-6-luna` wrote valid plans with the right default
  28/28 times, but prepared a variant for only 4–7% of the corrections one could have covered. That
  supports dropping them. Jev routed corrections right 135–138/140 times, and every correction it kept
  was right (58/58), so the system matched sending every correction to the LLM (137/140 both) and was
  ~20× faster only for chatter and pause (~0.1 s vs 2–2.5 s). No Jev mistakes on kept corrections,
  so the gate went untested; keep 0.7. A replan takes 2.7–4.1 s median, 6–7 s p95, with 11–25 s
  outliers (a 30 s timeout on `gpt-6-sol`). The hold-at-a-safe-point rule must cover that tail.
  `gpt-6-luna` matched Terra's accuracy at ~1/20 of the cost ($0.0003 vs $0.006 per replan): the
  default fast LLM.

**What the E12 update must do** to test this design:

1. One decision request per event, with the three question groups, for every source (user text,
   scene change, step finished or failed, new plan).
2. Replan with an LLM on escalation (a mock LLM offline), from the current world state, with no
   prepared variants.
3. Progress and plan checks as one question per object; code compares.
4. Escalate on the weakest relevant confidence, with a threshold per route.
5. The Spotter group handles any change the robot didn't cause, with instructions that don't restate
   the oracle's thresholds.
6. A literal "where the arm is in the plan step" fact; rerun `raw`.
7. A loop detector.

## Alternative to test: rules instead of steps

Instead of an ordered list of steps, the LLM picks the skills relevant to the task and writes a short
priority list of rules, and Jev re-checks their conditions on every event; the first rule whose
condition holds runs. This is a teleo-reactive program (Nilsson), and close to the Doom demo, where
the rules are hand-coded because the game never changes.

```
1. when a hand is near the arm            → hold
2. when a red block is on the table       → move_object(that block, left_bin)
3. when every red block is in left_bin    → done
```

- **For:** disturbances need no replan (the rules still apply; Jev picks the one now true), and
  checking plain conditions is what Jev is good at.
- **Against:** conditions must be checkable locally, and any ordering must sit in rule priority or
  be computed by code ("the lowest-numbered block not yet in the tray"): E11 showed Jev can't rank,
  and E12 `raw` showed it can't sequence when the state leaves its position implicit. Corrections still
  go to the LLM, because they change the rules.
- **Test:** the same walk scenarios run both ways, comparing accuracy and how often each needs the
  LLM.

**Follow-up: rules plus the decision loop.** The LLM writes the rules once; Jev runs them and handles
interventions with the same one-request decision. Each kind of surprise then has a cheap path:

| What happens | How it's absorbed | LLM? |
|---|---|---|
| A block is moved or removed | Rules still apply; Jev re-checks conditions and the right rule fires | No |
| A hand reaches in | Right-now answer: pause, back off | No |
| No rule applies, or two conflict | An event; the Router escalates | Fast LLM adds or fixes a rule |
| "Actually, right bin" | Router sends it to the LLM, which rewrites the affected rules | Yes, changed rules only |
| Chatter | Router: continue | No |

The LLM sets the policy; Jev adapts within it on every event, so the multi-second replan happens
only when intent changes, not when the world does.

## Open questions

- What the arm does while an LLM replans: carry on to the end of the current step, or hold at once.
- Threshold per route, and whether escalation (stay local, fast LLM, capable LLM, ask the user) works
  better as one ordered score, as in TypeSafe's entity alignment cookbook.
- Whether a 3–7 s replan wait (E13) is acceptable on every correction, or the arm should carry on
  through the current step while the LLM works, and what it does in a 25–30 s tail.
- When the fast LLM is enough and when the capable one is needed.
- Replan speed: a smaller output (only what changes) and prompt caching first; a faster model
  later.
