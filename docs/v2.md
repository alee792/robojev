# v2: Planner, Router, Sequencer, Spotter

v1 showed that Jev can run inside a real-arm control loop (138 ms median, no errors) and is good at
matching words to objects and places. It did not show that Jev beats a script: the task was
scriptable, and the script ended up in its prompt (`docs/assessment.md`). v2 gives each part only the
job it is good at.

## Principles

- **Jev chooses; code moves.** Jev picks among options code has already checked. Code owns
  geometry, arithmetic and limits.
- **The LLM is never on the critical path.** The arm always has something sensible to do without
  waiting for it.
- **Ask Jev only what code can't answer**, and show what gets worse without each question.
- **Safety never depends on a model.**

## Layers

| Layer | Runs on | When | Job |
|---|---|---|---|
| Perception | VLM + depth/tracking | VLM once per new object; tracking at frame rate | Produce the world state |
| Router | Jev | A correction, a skill failure, a change the Spotter can't place, or low confidence elsewhere | Decide who handles it (below) |
| Sequencer | Jev | A skill finishes or fails | Keep the plan on track: check progress against the task, adjust within the plan, or hand to the Router (below) |
| Spotter | Jev | Perception sees a change the robot didn't cause | Classify the change and pick an intervention (below). Overrides the Sequencer |
| Planner | LLM: a fast model, or a more capable one | New task, or when the Router hands off | Turn the task into a plan, or repair it |
| Skills | Code | While running | Execute; report done or failed |
| Safety filter | Code | Every command | Clip to workspace, speed and constraints |

## Keeping the plan on track

The plan comes from a fast model and can be wrong, so a task can fail with nothing outside changing.
After each skill the Sequencer checks progress against the task (the user's words), not just the
plan, and picks: carry on, retry, skip, choose a different next step from the plan, or hand to the
Router when the plan itself looks wrong. Code checks what it can measure (the gripper is holding
something); the Sequencer judges the rest ("is the tray going the way the user asked?").

Two failure sources, two layers: the Sequencer catches problems the robot or the plan caused, the
Spotter catches changes from outside.

## Spotting changes

Perception flags any change the robot didn't cause: an object moved, appeared or vanished, or
something isn't where the plan expects. Code detects the change; the Spotter decides what it means
and picks one intervention:

| Change | Intervention |
|---|---|
| The block the arm is going for was moved | Re-target it |
| A sorted block was taken back out | Put it back on the to-do list |
| A hand reaches toward the arm | Pause, or back off |
| A block flickers in and out (sensor noise) | Ignore |
| A new object appears on the table | Hand to the Router |

The code safety filter keeps its own hard limits, including a stop distance around hands, whatever
the Spotter decides.

## Routing

The Router keeps execution moving across the layers. For each event it picks one route, in the same
request as any parameter changes:

| Route | Example | Cost |
|---|---|---|
| Continue | Chatter from the user | None |
| Adjust | "Actually, reverse it": set the sort order parameter | ~150 ms |
| Fast LLM | "Not that one"; a grasp failed twice | ~1 s |
| Capable LLM | A new task; the plan no longer fits the table | Seconds |
| Stop / ask the user | "Stop"; a request it can't make sense of | Until the user answers |

Escalating when it wasn't needed costs time; carrying on when it should have escalated can cost a
wrong action. So low confidence means escalate. The arm keeps running or holds at a safe point while
an LLM works; it never waits mid-motion.

## Terms

| Term | Meaning |
|---|---|
| World state | Objects (id, name, position, attributes) plus robot state (holding, current skill, last result) |
| Task | What the user asked for |
| Plan | An ordered list of skills with objects and parameters filled in |
| Parameters | Settings in the plan that a correction can change: sort order, pace |
| Change | Something in the world the robot didn't cause: an object moved, appeared or vanished |
| Intervention | What the Spotter tells the arm to do about a change |
| Constraint | A rule that holds for the whole task ("don't touch the green one"). It attaches to a tracked object, so it moves with it |
| Instruction / correction | Text from the user; a correction is one given mid-task |
| Route | Where the Router sends an event: continue, adjust, fast LLM, capable LLM, stop |
| Skill | A capability with preconditions and a done/failed result |
| Safety filter | Code that clips every command to limits and constraints |

## Skills

```
precondition(world_state) -> bool   # the Sequencer only sees skills that can run now
start(args)                         # objects and parameters from the plan
step()                              # a short chunk of motion; the safety filter clips it
status() -> running | done | failed(reason)
```

Skills are scripts for now. The interface is the same one a VLA policy would use, so a dexterous
skill can be added later without changing anything around it.

## Example: a mid-task correction

The task is "line blocks 1-6 up in the tray, ascending". The plan has a `sort order` parameter,
and code computes the next block for either order. Blocks 1 and 2 are placed and the arm is carrying
3 when the user types "actually, reverse it".

| t | What happens |
|---|---|
| ~150 ms | Router: adjust, sort order = descending, after this block |
| ~150 ms | Code switches the parameter; the next block is now 6 |
| 0-3 s, in parallel | Blocks already in the tray are ambiguous, so the Router also hands that part to the fast LLM, which amends the plan or asks |

A correction that no parameter covers is routed to an LLM: the arm stops at a safe point and holds
while it replans.

This is the headline demo: the task changes in plain language mid-run, with no restart. Whether Jev
alone can handle "reverse it", or it needs the fast LLM, is what E11 tests.

## Rules that hold everywhere

- Priority: STOP button > safety filter > Spotter > Router > Sequencer > plan.
- STOP never depends on a model. A stop chosen by a model is only a pause: it resumes when the user
  says so or the Router decides to.
- Perception only flags changes the robot didn't cause. Code keeps a simple expectation of what the
  robot itself moves: the held object travels with the gripper, and objects within a few cm of a
  grasp may shift.
- Jev layers run on events, never on a clock, which keeps them well under the 20 requests/s account
  limit.

## Data capture

Every run records every Jev request and answer, every LLM call, the world state at each decision and
a camera frame at each event. A decision someone marks wrong gets its correct answer attached, and
the growing set is re-run on every prompt change. E12's logs are the first entries.

The dashboard shows each route, intervention and plan change as it happens, and is where a wrong
decision gets marked. Its design gets its own pass.

## Stages

- **Crawl:** sort blocks into bins or a tray on a static table, with several sorting rules and no code
  changes. Scripted skills; build in sim, accept on the real arm. Perception stays cheap: coloured,
  numbered blocks, an overhead camera with AprilTag calibration, colour plus depth for position, and
  a VLM only to read each block's number once.
- **Walk:** a person interferes: moves the target, takes a block back out, reaches into the path.
  Pass = the task still finishes, with no contact with the hand. Compared against the same system
  with the Spotter and Router replaced by hand-written rules, with some changes and corrections the
  rules can't anticipate.
- **Later:** VLA skills for objects a script can't handle, and a Planner that streams its plan in
  pieces so the first steps run while it works out the rest.

## Spikes

- **E11** (`experiments/e11_reorder.py`): one decision after "reverse it". Can Jev work out the new
  order itself, or only map the correction onto code's answer?
- **E12** (`experiments/e12_blocksworld.py`): a text-only blocks world run closed-loop through the
  Sequencer, Spotter and a Listener (the Router's first version), with a scripted person and runs
  with each layer switched off. Its code still uses older terms (Listener, knobs, utterance, orders).

Both need a TypeSafe key to run; see `docs/handoff.md`.

## Open questions

- How many parameters a plan should expose.
- What the arm does while an LLM reviews a correction: carry on, or pause at a safe point.
- Router thresholds: how confident is confident enough to continue without an LLM.
