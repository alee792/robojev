# v2: one decision per event

A robot arm that takes a task in plain language, carries it out, and adapts when the world or the
user changes something mid-task, without a restart. Three kinds of intelligence share the work: an
LLM plans, Jev (a fast classifier, ~150 ms per request) decides what each surprise means and who
should handle it, and code moves the arm.

## Principles

- **The LLM reasons.** It turns the task into a plan: which objects go where, in what order, and how
  to tell when the task is done. When the task changes, it replans from where things stand.
- **Skills move.** A skill is a motor capability (move an object somewhere, hand it over, stack it).
  It knows how to move the arm, not why.
- **Jev judges meaning, event by event.** For every event it decides what the arm should do right
  now, whether the plan can absorb it, and who should handle it. It chooses among options code has
  already checked.
- **Code does the numbers.** Geometry, arithmetic, ordering by value, limits and safety.
- **The arm keeps moving.** While an LLM works, Jev decides whether the arm carries on or holds at a
  safe point; only the first plan of an episode is a wait.
- **Plans cover the task as asked.** Surprises are handled when they happen, by the decision and, if
  needed, a replan.
- **Every Jev question earns its place:** each one is there because code can't answer it.
- **Safety is enforced in code**, independently of every model.

## Parts

| Part | Runs on | Job |
|---|---|---|
| Perception | VLM + depth/tracking | Keep the world state: every object, where it is, what it is. Flag changes the robot didn't cause |
| Planner | LLM: a fast model, or a capable one | Write the plan at the start of an episode; replan when a decision hands off to it |
| Decision | Jev | For each event, answer three groups of questions in one request (below) |
| Harness | Code | Hold the plan and world state; turn events into decisions; apply the answers; run the plan steps |
| Skills | Code (VLA policies later) | Motor control: carry out one plan step; report done or failed |
| Safety filter | Code | Clip every command to workspace, speed and constraints |

## An episode

Two loops run at different speeds:

- **The control loop** (code, ~100 Hz) moves the arm through the current plan step, with the safety
  filter on every command. Jev is not involved.
- **The decision loop** runs when an event happens. Each decision takes ~150 ms.

```
episode(task):
    plan = fast_llm(task, world)              # the one planned wait (a few seconds)
    start plan step 1                          # the plan check runs alongside
    decide("new plan")                         # a problem it finds is just another event
    until done:
        run the current plan step              # code, ~100 Hz, safety filter on every command
        on any event (plan arrived, step done/failed, scene change, user text):
            a = jev(event, where we are in the plan, nearby objects)   # three groups, ~150 ms
            apply a.right_now                  # carry on, hold, pause, back off, re-target
            if a.route == stay_local and confident:
                apply a.in_plan_fix            # retry, skip, re-queue, another step first
            else:
                plan = llm(a.route, task, world, plan, event)   # the arm carries on or holds, per a.right_now
                decide("new plan")
```

Worked through for **"Line the numbered blocks up in the tray, lowest number on the left"**, with
blocks 1, 3, 5, 7, 11, 12:

| Time | Event | Decision | What happens |
|---|---|---|---|
| 0-3 s | Task arrives | none | Fast LLM works out the order and writes the plan: 1 → slot 1, 3 → slot 2, … 12 → slot 6 |
| 3 s | Plan arrived | Checked alongside: every block has a place, in the right order | Step 1 starts at once: block 1 to slot 1 |
| 8 s | Step finished | Block 1 is in slot 1; next step | Block 3 to slot 2 |
| 12 s | Scene: someone slides block 5 aside | Right now: carry on. Route: stay local (the plan still holds; block 5's new position is used when its step comes) | Arm carries on |
| 14 s | Step finished | Next step | Block 5 to slot 3, from its new position |
| 16 s | User: "actually, highest on the left" | Right now: hold (the move in progress would put block 5 in the wrong slot). Route: fast LLM | Arm holds block 5 at a safe point; LLM replans: every block's slot changes, blocks 1 and 3 move again |
| 19 s | Plan arrived | Checked: matches the corrected task | Block 5 to slot 4; then the rest of the new plan |
| 22 s | Scene: hand reaches toward arm | Right now: pause (the code stop distance applies regardless) | Arm pauses |
| 23 s | Scene: hand gone | Right now: resume | Arm resumes |
| 60 s | Step finished | Every block is where the corrected task wants it | Episode over |

Most decisions are the routine "step finished" kind. The interesting ones are the few whose route
is not "stay local".

## The decision

Every event, whatever its source, gets the same request shape: the event, where the arm is in the
plan, and the objects near it. It carries three groups of questions, answered in parallel (asking
more questions in one request costs no latency, and code ignores the answers that don't matter for
this event).

| Group | Question | Answers |
|---|---|---|
| **Spotter** | What should the arm do right now? | carry on, hold, pause, back off, re-target, resume |
| **Sequencer** | Can this be fixed within the current plan? | retry, skip, re-queue an object, run another step first, none |
| **Router** | Who handles it? | stay local, fast LLM, capable LLM, ask the user |

Code combines them:

1. The **right-now** answer applies immediately. A typed "wait" is a pause just like a hand reaching
   in; while an LLM replans, right-now decides whether the current step carries on or holds.
2. The **in-plan fix** applies only if the Router says stay local and the confidence is high.
3. Otherwise the fast or capable LLM replans from where things stand.

**Progress checks ask one question per done condition** ("is it true that block 5 is in slot 3?"),
never "is the task on track?", which is multi-step reasoning Jev is weak at. Where code can measure
a condition directly (a block's position is inside a slot), code checks it and Jev isn't asked. A
plan check works the same way, with yes meaning something is wrong: "is block 7 something the task
asks about but the plan leaves out?"

**Confidence decides escalation.** Jev returns a confidence with every answer; the decision uses the
weakest confidence among the questions an action depends on, and escalates when it is below that
route's threshold. Thresholds are set per route, by what a wrong answer costs, and tuned as the
prompts are tested. A low-confidence detail falls back to the cautious choice.

## The plan

The LLM reasons from the task to motor actions. For the sorting task above:

```json
{
  "steps": [
    {"skill": "move_object", "object": "block_1",  "to": "tray_slot_1"},
    {"skill": "move_object", "object": "block_3",  "to": "tray_slot_2"},
    {"skill": "move_object", "object": "block_5",  "to": "tray_slot_3"},
    {"skill": "move_object", "object": "block_7",  "to": "tray_slot_4"},
    {"skill": "move_object", "object": "block_11", "to": "tray_slot_5"},
    {"skill": "move_object", "object": "block_12", "to": "tray_slot_6"}
  ],
  "done_when": ["block_1 is in tray_slot_1", "block_3 is in tray_slot_2", "…"],
  "constraints": []
}
```

The same shape covers tasks that aren't about arranging things: a handover is `hand_over(block_1)`,
done when "the person is holding block_1"; a tower is ordered `stack_on` steps; a standing rule ("keep
the green one off the tray") is a constraint. When a step can't run (its target slot is occupied),
that is an event, and the in-plan fix can run another step first.

Output is structured (a strict JSON schema, with object ids and places as fixed lists from the world
state) and kept small: a replan returns only what changes. The unchanging part of the prompt
(instructions, skill list) is cached.

## Skills

The first set is small and motor-only: `move_object(object, place)` (pick, carry, place),
`hand_over(object)`, `stack_on(object, base)`, `push(object, direction)`, `survey`, `hold`.

```
precondition(world_state) -> bool   # only steps that can run now are offered
start(args)                         # objects from the plan step
step()                              # a short chunk of motion; the safety filter clips it
status() -> running | done | failed(reason)
```

Skills are scripts for now. The interface is the same one a VLA policy would use, so a dexterous
skill can be added later without changing anything around it.

## Writing Jev questions

- **Code does the arithmetic.** Counting, ranking, distances and comparisons are computed; Jev gets
  the result or a named band ("near", "in the arm's path").
- **One judgment per question, one hop.** Loop over objects or conditions in code and ask each one
  directly.
- **Don't ask what code can look up.** Asking Jev for something code already knows invites
  contradictions.
- **Say exactly what you mean.** Jev reads literally: state the condition, put boundary cases in the
  criteria, and keep instructions and criteria saying the same thing.
- **Checks: yes means something is wrong.**
- **Name positions by role** ("the leftmost free slot", "the held block's goal"), not by arbitrary
  numbers.
- **State where the arm is in the plan step, literally** ("lowered at block 5's goal, not yet
  released").
- **Draw boundaries between competing options** with `not_for` in the criteria.
- **Ask about the action wanted, not the subject.** "Is the user asking the robot to do something
  different?" separates a correction from chatter; "is this about the blocks?" does not.
- **No voting on choices.** Below a confidence floor the answer is "uncertain" and escalates.
- **Filter the state** to the event and what's near it; irrelevant detail costs accuracy.

## Rules that hold everywhere

- Priority: STOP button > safety filter > right-now answer > route > in-plan fix > plan.
- STOP is handled in code: the STOP button, and "stop" typed by the user. A model can pause the arm;
  it resumes when the user says so or a decision says resume.
- Perception flags only changes the robot didn't cause. Code keeps a simple expectation of what the
  robot itself moves: the held object travels with the gripper, and objects within a few cm of a
  grasp may shift.
- A loop is a failure: the same two plan steps alternating more than twice escalates.
- Decisions run on events, which keeps them well under the Jev account's 20 requests/s.

## Data capture

Every episode records every Jev request and answer, every LLM call, the world state at each decision
and a camera frame at each event. A decision someone marks wrong gets its correct answer attached, and
the growing set is re-run on every prompt change.

The dashboard shows each decision, route and plan change as it happens, and is where a wrong decision
gets marked. Its design gets its own pass.

**Recording for training data.** Alongside the decision log, every episode can be recorded as a
robot-learning demonstration: camera frames and joint states at the control rate, the arm commands
sent, and per-episode metadata (the task, every correction, each decision and route, which plan step
was running, and whether every done condition was met at the end). The format is a standard
robot-learning dataset layout (such as LeRobot's), so any episode, simulated or real, can be used to
train a policy. Recording is off by default and switched on per run.

## Stages

- **Crawl:** sort numbered blocks into a tray and bins on a static table, with several different
  tasks and no code changes. Scripted skills; build in sim, accept on the real arm. Perception stays
  cheap: coloured, numbered blocks, an overhead camera with AprilTag calibration, colour plus depth for
  position, and a VLM only to read each block's number once.
- **Walk:** a person interferes and corrects: moves blocks, takes one back out, reaches into the
  path, changes the task mid-run. Pass = the task still finishes, with no contact with the hand.
  Compared against the same system with Jev replaced by hand-written rules, including some changes
  and corrections the rules can't anticipate.
- **Later:** VLA skills for objects a script can't handle, and a Planner that streams its plan in
  pieces so the first steps run while it works out the rest.

**Held-out tests.** Every test set keeps tasks and corrections that prompts are never tuned on,
reported separately: at least a stack, a handover and a standing rule, and corrections written by
someone else or generated from a different prompt.

**Headline demo:** the task changes in plain language mid-run ("actually, highest on the left"), with
no restart. Jev reads the correction within ~150 ms and decides whether the arm carries on or holds;
the fast LLM works out the new order and replans in a few seconds.

## Use case: a data flywheel

Human teleoperation is slow, costly and hard to scale, and rarely captures recoveries from mistakes.
This harness can act as the teleoperator instead, producing demonstrations that train policies which
then replace its own scripted skills:

1. **Pick a task** people want training data for.
2. **Work it out slowly.** A capable model plans it in simulation (plan, done conditions, any missing
   skills) and runs it once, slowly; success is checked by the done conditions and a person.
3. **Distill it into a recipe** the fast harness runs: plan template, Jev question templates, skills.
   A small LLM, Jev and the skills then run it quickly and cheaply.
4. **Vary and record.** Randomise object positions, counts, colours and lighting; add scripted
   disturbances and corrections; record every episode with its language and success label.
5. **Train** a policy on the successful episodes.
6. **Evaluate and swap.** If the policy beats the scripted skill on held-out variations, it replaces
   that skill (the skill interface allows it), and the loop runs again with harder variations.

What this adds over teleoperated data: recoveries from disturbances, corrections in plain language,
success labels for free, and scale in simulation. Its limit: data is only as good as the skills that
produce it, so dexterous skills still need human demonstrations to start from. Each turn of the loop
is judged on held-out variations, with a person spot-checking a sample, so the flywheel can't drift
by training on its own quirks.

## Alternative to explore: rules instead of steps

Instead of an ordered list of steps, the LLM picks the skills relevant to the task and writes a short
priority list of rules; Jev re-checks their conditions on every event, and the first rule whose
condition holds runs. This is a teleo-reactive program (Nilsson), close to how a game agent's
hand-written behaviour works.

```
1. when a hand is near the arm                           → hold
2. when the lowest-numbered block not in the tray exists → move_object(it, the next free slot)
3. when every block is in the tray                       → done
```

Conditions must be checkable one at a time, and any ordering sits in rule priority or is computed
by code (as "lowest-numbered" is above).

**With the decision loop**, the LLM writes the rules once and Jev runs them and handles
interventions, so each kind of surprise has a cheap path:

| What happens | How it's absorbed | LLM? |
|---|---|---|
| A block is moved or removed | Rules still apply; Jev re-checks conditions and the right rule fires | No |
| A hand reaches in | Right-now answer: pause, back off | No |
| No rule applies, or two conflict | An event; the Router escalates | Fast LLM adds or fixes a rule |
| "Actually, highest on the left" | Router sends it to the LLM, which rewrites the affected rules | Yes, changed rules only |
| Chatter | Router: continue | No |

The LLM sets the policy and Jev adapts within it on every event, so the multi-second replan happens
only when intent changes, not when the world does. To compare: the same walk scenarios run with steps
and with rules, measuring accuracy and how often each needs the LLM.

## Deferred

- **Planner and Jev prompts.** A proper system prompt for the planner: what the desired end state
  looks like, intermediate states, the skills and how each changes the world state. Parts of this
  (skill effects, what counts as done) go into Jev's question context too.
- **A slow heartbeat decision.** Besides events, a decision at a low, configurable rate as a check
  that the arm is still aligned with the task. Off until needed.

## Open questions

- **Escalation as one ordered score.** The Router's routes run from least to most help: stay local,
  fast LLM, capable LLM, ask the user. Instead of a choice among them plus a threshold per route, one
  Jev *score* question whose levels are those routes would let Jev place each event on that ladder
  directly (the pattern in TypeSafe's entity-alignment cookbook). Worth testing against the choice.
- **Fast or capable LLM.** Which events need the capable one; decided by the Router's question
  criteria, refined as the prompts are tested.
- **Replan speed.** Continuity comes first (the arm carries on where it can); then a smaller output
  (only what changes), prompt caching, and later a faster model.

## Terms

| Term | Meaning |
|---|---|
| Episode | One task, from the user asking to done, stopped, or given up |
| Task | What the user asked for: the final arrangement. The order of moves is up to the plan unless the user says otherwise |
| World state | Objects (id, name, position, attributes) plus robot state (holding, current step, last result) |
| Plan | From the LLM: an ordered list of plan steps, the conditions that mean the task is done, and any constraints |
| Plan step | One skill call with its objects filled in: `move_object(block_5, tray_slot_3)` |
| Skill | A motor capability: move an object somewhere, hand it over, stack it. No task logic |
| Done condition | A plain statement the LLM writes and Jev or code checks: "block_5 is in tray_slot_3" |
| Event | Anything that needs a decision: a plan arrives, a step finishes or fails, the scene changes, the user types |
| Decision | One Jev request with three question groups, plus code combining the answers |
| Route | Who handles an event: stay local, fast LLM, capable LLM, or ask the user |
| Constraint | A rule that holds for the whole task ("don't touch the green one"). It attaches to a tracked object, so it moves with it |
| Safety filter | Code that clips every command to limits and constraints |
